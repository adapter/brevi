# @brevi/worker

The `brevi worker` daemon. Holds today's execution stack behind the dispatch protocol in `@brevi/shared`'s `worker.ts`: dials a `brevi` host over one outbound WebSocket, executes whatever it dispatches in a bwrap sandbox, and mirrors every run mutation back over that socket. The host is a scheduler; every run's sandbox lives on the worker that executed it. A worker only ever dials out, it never listens, and its `sandbox.*` config (concurrency, timeout, retention) is read from its own local `~/.brevi/config.json`, never trusted from the host.

## Layout (src/)

- `daemon.ts`: `runWorker()`, the entry point. Loads local config, resolves the sandbox provider, connects, and routes every host message (dispatch, cancel, discard, attach-*) to the right handler until SIGINT/SIGTERM
- `connection.ts`: the outbound WebSocket client: enrollment (which auth envelope each attempt presents), register, heartbeat, exponential backoff with jitter on a drop, a bounded generic queue for everything else that flushes in order after the next successful registration, and a per-lease replay buffer (with worker-assigned, per-lease sequence numbers) for the five lease-scoped reporting frame types, replayed once the host's `lease-ack` says where it got to
- `reporter.ts`: `RunReporter`, a `RunSink` that mirrors every run mutation to the host as `run-patch`/`run-event`/`run-artifact` messages instead of writing to a local store
- `sink.ts`: `RunSink`, the seam `runner.ts`/`followup.ts` were written against instead of the host's `RunStore` directly (see the doc comment there for why)
- `attach.ts`: worker-side interactive sessions (`brevi attach`, the dashboard's web terminal): rehydrates a finished run's retained sandbox, reprovisions credentials, and bridges its PTY to the host over attach-* messages
- `identity.ts`: this machine's enrollment record (`~/.brevi/worker.json`, mode 0600): the id the host assigned it, the durable credential it earned, and the host that issued them
- `runner.ts` / `followup.ts`: one run end to end (moved from `@brevi/orchestrator`, largely unchanged; see internal.ts in that package for what they still borrow from the host side)
- `prompts.ts`, `limits.ts`-adjacent bits, `costs.ts`, `ccusage.ts`, `provision.ts`, `resume.ts`, `review.ts`: the rest of the execution stack, also moved from `@brevi/orchestrator`

## Gotchas

- A worker does not invent its own id: `--token` carries a single-use pairing token, the host redeems it once and answers `registered` with the assigned id plus a durable credential, and `identity.ts` stores that in `~/.brevi/worker.json`. Every later connect presents the credential instead. A supplied token is always tried first, even when a credential is stored (that is how a revoked machine re-enrolls in one command), and falls back to the stored credential when the host answers `invalid-token`/`expired-token`. Branch on `rejected.code`, never on its prose.
- Drain and revoke arrive over the channel, not from local config: `worker-state` (and every `heartbeat-ack`) carries the operator's state, so `draining` rejects new dispatches with `"worker is draining"` while runs already in flight finish and report normally, and `revoked` deletes the stored credential, runs the same graceful shutdown a SIGTERM does, and exits non-zero rather than reconnecting into a rejection loop.
- The daemon survives a machine with no `~/.brevi/config.json` at all (a worker never has to run `brevi init`): `loadConfig` failing falls back to `CONFIG_DEFAULTS` (bwrap, concurrency 1). Sandbox settings still come only from the worker's own config, never from the dispatch.
- The dependency with `@brevi/orchestrator` runs one way: this package imports node-side helpers (GitHub, Linear, R2, usage-limit and memory helpers) from `@brevi/orchestrator/internal`, but the orchestrator never imports `@brevi/worker` or `@brevi/sandbox`. `grep -rn "@brevi/sandbox" packages/orchestrator` must stay empty, which CI enforces.
- `runner.ts`/`followup.ts` know nothing about sockets or leases: they only see a `RunSink`, the dispatch's prompt policy, and a couple of memory-recall callbacks on `RunContext`. All the wire-protocol plumbing lives in `reporter.ts` and `daemon.ts`, so the run pipeline itself reads the same whether it once ran on the host or now runs here.
- A patch handed to `RunSink` stays domain-shaped: naming a field with an explicit `undefined` clears it, and `RunReporter` is what translates that into the wire's `null` (`sandbox` included, one level deeper). Nothing outside `reporter.ts` should know the `null` convention exists.
- Holding a lease and executing a run are two different things (`claimedLeases` and `activeRuns` in `daemon.ts`). A lease is claimed from dispatch until the host's `run-complete-ack`, so a run that finishes while the socket is down is still listed on the next `register` and its buffered completion replays instead of the host stranding it. Removing a lease on anything other than that acknowledgement reintroduces the bug.
- Shutdown order is load-bearing (see the comment in `daemon.ts`): stop accepting dispatches, abort the active runs, await their executions, drain the outbound queue, and only then close the socket. Closing earlier drops a run's final `run-complete` forever; skipping the abort or the await leaves sandboxed children running with nothing left to report their exit.
- A worker forgets everything about runs it executed before its last restart: `knownRuns` in `daemon.ts` starts empty on boot, so leftover workspace directories are swept unconditionally and `brevi attach` to a sandbox retained before a restart won't find it. A later fleet iteration can persist enough state to survive a restart; this one keeps it simple.
- Artifacts only exist on the worker's disk (the host's `RunStore` has no filesystem access to it), so `RunReporter.addArtifact` reads the file and ships its bytes as base64 in a `run-artifact` message, skipping (with a logged system event) anything over `WORKER_MAX_ARTIFACT_BYTES`.
- The hosted one-line installer lives at `scripts/install.sh` (POSIX sh, published at `https://brevi.dev/install.sh`), not under `src/`; it is not part of the TypeScript build. It provisions a `brevi` system user, bubblewrap, and `brevi-worker.service`.
- The worker unit execs a tiny wrapper (`/usr/local/lib/brevi/worker-start.sh`) that assembles the real command's arguments from environment variables; the unit file itself never changes when a setting (host, name, concurrency) changes, only the env file does, so no `daemon-reload` is needed for a settings change.
- Those variables reach the wrapper through the unit's `EnvironmentFile=`, which systemd parses as data. The wrapper never sources an env file: a worker name of `build worker` would otherwise run `worker` when the file is sourced. Values are whitelist-validated before being written.
- A re-run of the installer ends by restarting `brevi-worker.service`, not `enable --now` (which does nothing to an already-active unit), and confirms the result from the unit's own journal: it waits for the `[brevi] registered with ... as worker` line `connection.ts` logs, matched only in what the restarted process wrote (`journalctl --since` a timestamp taken before the restart). Not an HTTP call to the host: the address in a pairing command is the worker channel's listener whenever `fleet.host` is set, and that listener serves nothing but the authenticated `/ws/worker` upgrade, 404ing `/api/health` and `/api/workers` by design. The preflight's egress check accounts for the same thing: any HTTP answer from `--host` counts as reachable, since that is what it is really testing.
- The installer never enrolls a machine itself: it writes the pairing token as `BREVI_TOKEN` into `/etc/brevi/worker.env` (0640 root:brevi), the wrapper passes it as `--token` on the first start, the daemon redeems it once for the credential in `~/.brevi/worker.json`, and the installer deletes the line as soon as the host confirms that worker connected. Steady-state restarts therefore carry no secret in the unit, the env file, or `ps` output.
- `brevi-worker.service` runs with no added capabilities: bwrap uses unprivileged user namespaces.
- A lease-scoped reporting frame (`run-patch`/`run-event`/`run-artifact`/`run-memories`/`run-complete`) lives in exactly one place, its lease's replay buffer in `connection.ts`, from the moment `send()` stamps its `seq` until the host's `lease-ack` or `run-complete-ack` says it's been applied; it is never also queued in the generic outbound queue, since that would let a reconnect deliver it twice. Nothing may send a frame past a lease that is still `awaitingAck`: a socket close marks every lease `awaitingAck` again, and only a `lease-ack` (the normal path) or the `REPLAY_UNBLOCK_MS` backstop (a host that never answers one) clears it and lets the buffer's contents go out.
- Dropping a frame to hold the replay buffer under `WORKER_REPLAY_BUFFER_LIMIT` punches a hole in that lease's sequence numbers, and the host's watermark will not cross a hole on its own. So every drop is announced: `gapThrough` moves up to just below the oldest frame still held (by definition the point below which everything is either acknowledged or dropped) and a `lease-gap` says so. It travels through the *generic* queue, never the lease's own buffer, since the buffer is exactly what is stuck behind the hole, and it is re-sent on every registration in case the host restarted before its debounced watermark write landed. Drop that frame and the buffer grows forever behind a watermark that can never advance.
- A run must never outlive its lease: once it expires the host is free to give the run to another worker, and two workers pushing the same deterministic branch is the failure this prevents. The worker fences itself, because the case that matters most (a partition that never heals) is the one where no frame from the host can arrive: every `lease-ack` restates `expiresAt`, and `sweepLeaseDeadlines` aborts the run once it passes. The host's explicit `lease-lost` covers the other case, a worker that rejoins still claiming a lease that is gone.
- Handing a frame to a socket is not delivery, so `delivered` is only a within-session guard against sending the same frame twice, never a record that the host has it. A `lease-ack` repeating the watermark it gave last time means a whole heartbeat interval passed with no progress on frames the host already has (a write that failed host-side), so the still-unacknowledged ones are cleared from `delivered` and go out again. Without that, a failed `run-complete` would sit in its buffer until some unrelated disconnect, while heartbeats renewed the lease indefinitely.
